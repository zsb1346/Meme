## 键数预设：口径改成「八度」（用户要求「把数量调整一下」）

用户原话：**「不是有一个 预设 键数吗 把数量调整一下 普通的无半音数量和有半音的数量

### 设计

| 档位 | 无半音 | 有半音 | 音域 |
|---|---|---|---|
| 1 个八度 | 7 键 | 12 键 | C3–B3 |
| 2 个八度 | 14 键 | 24 键 | C3–B4 |
| 3 个八度 | 21 键 | 36 键 | C3–B5 |

口径从「键数」改成「**八度数**」→ 同一档在两种模式下**音域完全相同**，打开半音
只是把这段音域**切得更细**（14 → 24），不是把范围换掉。
`CountOption` 的值随之从 `'7'|'14'|'21'` 改成 `'1'|'2'|'3'`，label 改成
`1 八度/2 八度/3 八度`（title 给出「n 个八度 · x 键 · C3–Bx」）。
单一来源 = `pitch-map.keyCountPresets`（原先 7/14/21 散在 3 处硬编码）。

### 顺出来的真 bug：档位 + 切模式 → 音域漂移（已修）

```
自然音 14 键（C3–B4）+ 打开半音 + 选「3 个八度」
→ 从 B4 往后接半音键 → 「C3–B4 全白键 + C5–A6 半音」= 音域 C3–A6
```

点的是「3 个八度」，拿到的是 C3–A6，任何操作顺序都中招（先点档位再开半音更糟）。

**修法：两条路彻底分开**（⛔ 不许合并）
- `setKeyCount` = **数量**：步进器 ± 走这条，增删末尾，**不动任何已有键的音高**。
- `realignKeys` = **音域**：档位走这条，第 i 个键 = `sequencePitchAt(i)`，**保留装配**
  （`sequence`/`cursor`/绑定按位置留下），只改 `pitchMidi` 与**自动生成的**音名标签。
- 重排会移动已有键音高 → hook 侧 `applyKeyRange` **toast 告知**
  （实测文案：「键集已按半音音阶重排，13 个已有键的音高随之移动（装配保留）」）。
- 新增 `src/model/key-range.test.ts`（7 例，含「setKeyCount 绝不重排」的反向断言）。

## MIDI 导入优化（用户：「键位都改得跟标准的差不多了，我们也得优化 Midi 导入功能了」）

### 病根

旧导入的反馈只有一句「已导入 N 个音符」。而**太短被丢、超上限被截断、多轨被合并、
多少音落在黑键、超域丢了多少** —— **全部静默**。用户拿到一个少了 1/5 音的工程，无从自查。

### 改法：两段式

```
engine/midi-import.parseMidiFile(file)   ← 只读文件 + 逐轨体检，零工程写入，可取消
        ↓  弹窗预览 / 勾选轨道（摘要实时重算）
engine/midi-import.buildMidiTake(parsed, opts)  ← 确认后才落盘
```

- **`MidiImportSummary`**：`tooShort / belowRange / aboveRange / truncated / keptEvents /
  blackKeyEvents / neededLanes / fits`，**每一类丢弃都有独立计数**。
- **⭐ 摘要与落盘走同一个 `midiToTakeEvents`** → 预览的数字与最终的结果**不可能不一致**。
- **`MidiImportModal.tsx`（新建）**：轨道勾选（空轨禁用 + tooltip 说明）、音域条
  （当前键盘 / 自动扩容段 / 歌曲实际音域）、「会有 N 个音进不来」拆分原因块。
- 落盘后**自动做两件事**：音域不够就扩容；含黑键就翻开半音键（否则那些键没地方点）。
  **顺序固定：先 `setSemitoneMode(true)`、再 `setKeyCount(...)`**（反了会把格数对齐到白键格）。

### 顺出来修掉的一个静默失效

**`tailwind.config.js` 的 fontSize 写死像素**（`micro: '9px'`），而 `tokens.css` 早把
`--fs-micro` 调到了 11px → **那个变量从来没被消费过**，上一轮「字号上调」的改动在界面上
**一点效果都没有**。看代码完全正常、编译过、测试过，就是没变。已全部改成引用 CSS 变量。

### 验证

  弹窗实测「244 个音 / 1:09.3 / 160 BPM / G4–D6 / 半音音符 48 个（20%）/ 键盘音域 24→48」；

### ⚠️ 先踩了一个会毁掉全部结论的坑：我的「手机截图」根本不是手机尺寸

用 `--w=390 --h=844` 截了 7 张图，看着像手机、实际是 **491×692**
（`window.innerWidth` 回读 491）。根因：那参数是 `--window-size`，
**Windows 上 Chrome 有最小窗口宽度（实测钳到 491px）**。
→ 差一点就基于错误尺寸得出错误结论。

**修法**：给 `scripts/cdp-shot.mjs` 加 `--mobile`，走
`Emulation.setDeviceMetricsOverride`（+ `setTouchEmulationEnabled`，`mobile:true`），
**必须在 `Page.navigate` 之前下发**，否则首帧仍按窗口宽度布局、媒体查询界面会闪一下。
自检：`--eval` 回读 `{"iw":390,"ih":844}`。**⛔ 以后验收手机端一律带 `--mobile`。**

### 真机（390×844）实测到的病

- **制作台最惨**：工具区竖向堆叠吃掉 **262px（31% 屏高）**；
  「播放」竖排两行、「音频/电子音」一字一行、「自动修音」竖排四行；
  「**导出**」被右边缘裁成「**导**」；「待机」完全消失；卷帘画布只剩 364×515。
- **演奏台**：顶栏「+ 新建」裁一半；音域/声部行换 3 行且后面被裁；
  琴键 51×96 只手用 2 行 205px，**下方约 480px 全空**。
- **混音台**：EQ 最右 band 与 20k 刻度被裁；提示行
  「拖拽 · 滚轮 Q · 右键 · 双击 · Alt」**全是鼠标操作**。
- **素材箱**：文案写「把音频文件**拖到**这里」——手机上不存在拖放。
- 代码量化：`hover:` **85 处** · `onWheel` 11 · `onDoubleClick` 11 · `onContextMenu` 3。
  `shortcuts.ts` 是全项目唯一 keydown 入口（这点是好设计，替代点集中不会漏）。

### 四条理念（后面所有设计都是推论）

1. **修饰键 → 看得见的模式**。桌面「手势 × 修饰键」的二维塌缩成一维会撞车，
   唯一出路是把修饰键提升为屏幕上的模式开关。但模式有病：**隐形状态会被忘记**。
   → 两条硬规矩：**模式必须常驻可见**（托盘那一格一直亮）+ **点画布不能进模式**。
2. **一块屏装不下三块面板 → 切层，不挤压**。挤压的尽头是单字竖排，那不是界面。
3. **⭐ 手机上「弹」比「编」重要 → 键盘必须常驻**。手机的强项是多指拍屏 + 随身，
   不是精细编曲。核心循环是「拍 → 听 → 改一个音 → 再拍」，这个循环里
   **键盘和卷帘必须同时在场**（桌面免费，手机要画进布局）。
   → 反过来：**演奏台是手机端主角，制作台是配角**。
4. **手指没有 hover → 预判让位给显式**。桌面「点空白即插入、拖动则平移」靠 hover 预判，
   手指按下 50ms 内不知道意图 → 手机上**点空白永远是平移**，加音必须走显式「＋ 加音」模式。

### 顺带：手机端需要「能力探测」而不是只按宽度断点

桌面与手机的差异不只是宽度（还有 hover / 修饰键 / 物理键盘）→
布局可以用宽度断点，**交互分支必须用 `(hover: hover)` / `(pointer: fine)` 探测**。

### 三个真问题（前两个是「本地能跑、部署就死」）

| # | 问题 | 后果 |
|---|---|---|
| ① | `src/engine/rush/loader.ts` 里 `HAJIMI_WASM_URL = '/hajimi_audio.wasm'` **绝对路径** | 部署到子目录（`/meme-studio/`）→ 404 → **整个应用没声音** |
| ② | `src/engine/pitch-worker.ts` 里 `MODEL_URL = '/model.json'` 同样绝对路径 | 同上，AI 音高检测全废 |
| ③ | `@tensorflow/tfjs` **不在我们 `package.json`** —— 靠 `@spotify/basic-pitch` 的依赖被提升到 `node_modules` 根才解析成功 | 换机器 / 重装依赖就炸（隐式依赖） |

**修法**：①② 改用 `import.meta.env.BASE_URL`（worker 里用 `new URL(..., import.meta.url)`
走 Vite 的资源解析）；③ `package.json` 显式声明 `@tensorflow/tfjs`；
另外 `tsconfig.worker.json` 的 `types` 补 `vite/client`（它 include 了 `loader.ts`，
要用 `import.meta.env` 就得有这个类型）。

**之所以现在才发现**：这三个都是「dev server 在根路径跑 → 全部正常」的隐形问题。
**子目录部署是最强的探针**（`--base=` 一变，硬编码路径全部现形）。

### 环境坑（新增一条 SEVERE）

**`vite preview` / `python -m http.server` 都会被后台任务生命周期带走**
（症状：`curl` 返回 `000`、只剩 TIME_WAIT，页面变成 Chrome 错误页 → 探针读到 `chrome-error://`，
会把「服务器没了」误报成「算法坏了」）。
→ **正解：把「起服务器 + sleep + curl 健康检查 + 跑探针」放进同一条命令**，
别跨轮次依赖它活着。**dev server (5173) 反而活得久**，但同样不可依赖。

**探针自身的两个坑**（都被绕过了）：
- 判定太宽松会把「上传中」的占位条目当成成功 —— bodyText 里其实写着「解码中… 0.0s」。
- `sed` 替换占位符时只换了文件名、没去掉模板里原有的 `/assets/` 前缀，
  拼成 `/assets/meme-studio/assets/…` → **探针自己造出来的假 404**。
  改占位符要连**前缀一起替换**（`s#/assets/__X__#/meme-studio/assets/FILE#`）。
