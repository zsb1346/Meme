## 1. 弦鸣引擎「按下去完全没声」——真 bug，探针抓到的

`probe-synth.mjs` 新增的「七引擎逐个离线渲染」段当场抛
`InvalidStateError: cannot call start more than once`（**只有 string 中招**）。

根因：`trigger()` 里两条起振清单**共用同一个数组** `extraStarts` ——
通用循环 start 一次、弦鸣专属分支又 start 一次。异常逃出 `trigger()`
→ `noteOn()` 后半段（排自动释放 + 注册声部）整段跳过 → 该音色一个音都不出。

修法（按「一份清单只背一种语义」拆开）：

- `triggerStarts` —— `trigger` 负责 start（白噪声叠加支路、噪声引擎主源）。
- `extraStarts` —— **只登记回收**：粒子 grain、噪声换色的新源、弦鸣脉冲。
- `dispose()` 两个清单都遍历。
- `trigger` 的循环改遍历 `triggerStarts`。

⚠️ 单测当时 29 条全绿也没照出来：假 AudioContext 的 `MockSource.start()` 是**幂等**的。

# 手机端「电子音一卡一卡」定位（当日追加）

用户报：桌面正常，**手机端电子音有「一卡一卡」的感觉**。

## 新增探针 `scripts/probe-synth-mobile.mjs`

CDP + 手机视口（844×390 @3x）+ **CPU 节流 1/4/6/8x**。为什么必须新写：
vitest 没有 Web Audio；`probe-synth.mjs` 用 `OfflineAudioContext` —— **离线渲染不跑定时器、
也不存在「主线程被占住」**，它量的是出声没有、干不干净，量不到卡顿。

三个决定性量法（写进探针注释）：
① **包裹 `window.setInterval`** → 拿到引擎两个定时器回调的 count/总耗时/最大耗时；
② **包裹 `AudioContext.prototype.create*`** → 每次按键到底造多少节点；
③ **帧间隔只在演奏窗口内采样** → 否则最大值被模块加载污染成 1~3 秒（第一版就栽了）。

## 实测（6x ≈ 中端手机，一帧 16.7ms）

| 动作 | 1x 桌面 | 6x | 8x | 造节点 |
|---|---|---|---|---|
| 按一个键 | 2.1ms | 11.1ms | 17.3ms | **20.06 个** |
| 叠音 6 个 | 2.0ms | 11.1ms | 16.7/20.2ms | 20 个 |
| 首次进入电子音发声 | 81ms | **269ms** | **462ms** | 52 个 |
| 换音色 `loadSynthPatch` | 18–29ms | 157–242ms | 229–330ms | **0 个** |

⭐ **`setPatch` 分摊（本次最硬的一条）**：

| 倍率 | 全等 patch | 只改 1 个参数 | 拖动 1 个参数 | 拖动同一值 |
|---|---|---|---|---|
| 1x | 24.7ms | 25ms | 0.6ms | 0ms |
| 6x | **166.9ms** | 156.8ms | 1.5ms | 0.5ms |
| 8x | **275.2ms** | 208.3ms | 1.4ms | 2.2ms |

**「一个值都没变的全等 patch」也要 167ms** → **`setPatch` 的成本只与「patch 有多少键」有关，
与「改了多少」无关**：它对全部 117 个键**无条件**调 `writeParam`（无早退）。
而 `applyParam`（拖动路径）第一行就 `if (this.patch[name] === v) return;` → 1.5ms。

**推论（就是用户听到的那个卡）**：拖旋钮时每次移动走 `applyParam` = 1.5ms（不卡），
但松手 **120ms 尾随落库 → `store.setSynthPatch` → `engine.setPatch` = 167ms 冻结**；
触屏拖动常停停走走，防抖被反复触发 → **反复 167ms 冻结 = 「一卡一卡」**。
点预设 / 换引擎 / 重置走同一条路（0 个节点，纯 CPU）。

## 排除掉的三条（省得改错地方）

- ❌ **声部泄漏** —— 四档全绿：`created=29=disposed`、`live=0 dying=0`、排空 0ms。
- ❌ **250ms 清扫器** —— 最大 4.3ms（8x 下 5.8ms）。
- ❌ **16ms 调制节拍** —— **一次都没跑**（0 次）：classic + 无调制矩阵时它按设计自己停表。

## 另一条实测：`wavetable` 是全七个引擎里最重的

换完引擎后的第一个音：1x 4.2ms / 6x **32ms** / 8x **41.9ms**（要建 `PeriodicWave` + 双振荡器）。
其余引擎在 6x 下 7–23ms。

## 待定（尚未动手）

修法优先级：① `setPatch` 去重（零音色风险、纯性能，可用指标验收）；② 声部池化 / 降 20 节点数；

②改了发声路径 → 必须回到「耳朵定」那条规矩。

> 演奏和动画模式 按下一个按键(或者点击)的时候 对应的会播放一个变蓝的动画
> 但是 同时按多个的话 就只会有一个有动画 这样就很割裂 且 不能长按
> 期望: 按下多个按键的时候 同时都可以播放动画 且 可以支持长按

（「变蓝」= `flame400` 实为 `#409CFF`。名字叫 flame，颜色是蓝。）

## B. 根因：**状态粒度错了**，不是少了个判断

`src/hooks/useKeyAnimations.ts` 旧版：

    lastPress: { keyIndex, pressed } | null      ← 全局单槽
    pressTimerRef = setTimeout(→ null, 260)      ← 到点强制「松手」

- 多键同按 → 后按的键占住槽位，先按的键 `externalPress` 变 undefined，
  MemeKey 里 `else setPressed(false)` 把它画回未按下（手指还按着）
- 长按 → 260ms 到点槽位清空 → 动画自己结束

⇨ **旧版根本没有「按住」这个状态，只有「最近一次触发后的 260ms」。**
另一个隐藏项：`lastFlash` 也是单槽 → 300ms 内按两个键，前一个的闪灯被掐掉。

## C. 改法（五处）

1. **`src/hooks/key-anim-state.ts`（新）** —— 纯状态内核（无 React / 无 DOM，node 里可测）：
   `pressKeyIn` / `releaseKeyFrom`（集合）、`setFlashIn` / `clearFlashIn`（映射 + token）、`FLASH_MS`。
   - 无变化时**返回入参本身** → React 靠 `Object.is` 跳过重渲染（36 个键的重复点击路径）
   - 闪灯带 `token` → 200ms 内连点两次时，**第一次的定时器不许掐掉第二次的闪灯**
2. **`useKeyAnimations` 重写**：`pressedKeys: ReadonlySet` + `flashes: ReadonlyMap`；
   `pressKey`/`releaseKey` **事件驱动、零定时器**；每键一个闪灯定时器；
   `window.blur` / `visibilitychange(hidden)` → `clearPressed()`。
   ⛔ **松开事件是会丢的**：按住时 Alt+Tab 走掉，那一下 keyup 落在别的窗口 →
   键位永远卡在按下态。兜底必须有。
3. **`shortcuts.ts` 补 `registerKeyUp`**（文件头规则 #4 早就承诺「后续加」）。⛔ **keydown 与 keyup
   的语义相反**，照抄必错：**不短路**（keyup 要派发给所有匹配者）、`guardInput` 默认 **false**、
   **不设 `when`**、`keys` 可省略 = 收全部。顺带修掉 StudioPage 的裸
   `window.addEventListener('keyup')`（违反规则 #4）。
4. **`MemeKey`**：`externalPress` → `externalHeld`；显示值 `showPressed = pressed || externalHeld`
   （两个来源**取或**，谁也不能清掉对方）；删掉那个 `else setPressed(false)` 的 effect。
5. **两个消费端**（StagePage / StudioPage）：动画从共享的 `playNote` / `wrappedTapKey`
   移回**各自的输入路径**。⛔ 规矩：**谁发起的输入，谁负责这一路的动画**。
   指针路径归 MemeKey 本地态（各实例一份 → 多指同按免费成立），键盘路径归页面。

## D. ⚠️ 自己造的一个坑（靠探针抓出来）

键盘路径写成 `const result = playNote(i); if (result === null) return; pressKey(i);`。
而 `playNote` 在 **`handlePress` 返回 null（KeyMachine 未就绪）** 时也返回 null ——
那是「此刻出不了声」，不是「这个键不可演奏」→ 按了绑定键**毫无视觉反馈**。
修：`handlePress(i) ?? { triggered: false, slotIndex: null }`，`null` 只保留「不可演奏」一种含义。

**为什么单测测不到**：指针路径不受影响 —— MemeKey 的 `fire()` 在调 `onPress` **之前**就设好了
本地按下态。所以这个坑只在键盘路径显形（探针里表现为「指针全绿、键盘全红」）。

## E. ⛔ 同文件并行编辑会**静默互相覆盖**（今天的头号工具教训）

同一条消息里对 `MemeKey.tsx` 发了 3 个 Edit，**全部报「成功」，实际只落地 1 个**：
`transform:` 与两个 className 分支读的仍是本地 `pressed`，`showPressed` 那行**在但没被用上**。

- 症状：状态里明明有 `pressedKeys={0}`、StagePage 也重渲染了（插桩读到 `[0]`），
  但 `el.style.transform` 不变 → 只有键盘路径坏。
- 规矩：**同一文件的多处改动必须串行**（一次一个 Edit，等结果）。
- 更狠的一条：**`toContain('那行代码')` 只能证明「代码存在」，证明不了「被用上」**。
  第一版守卫就是这样被骗过去的（实机探针 S3 红了才暴露）。
  补强后的守则 = 钉**判据出现在决策点上**：
  `showPressed\s*\n\s*\?\s*'border-flame-400`、`transform: showPressed ? …`；
  反面 `/^\s*pressed\s*$/m`、`/:\s*pressed\s*$/m` 必须为假。

## G. 探针自己踩的三个坑（已写进探针注释）

1. headless 新目标**默认没有焦点** → 键盘事件没人收。鼠标 / 触摸按坐标命中不需要焦点，
   于是表现为「指针全绿、键盘全红」，极像功能 bug。修：`Emulation.setFocusEmulationEnabled`，
   **必须在 navigate 之前**。
2. `Input.dispatchTouchEvent` 两个方向语义**相反**：`touchStart` 的列表 = 全部活跃点
   （与上次求差 = 新增）；`touchEnd` 的列表 = **被抬起的那个点**。传反会得到
   「松开甲、乙灭了」这种像 bug 的结果。
3. `Emulation.setTouchEmulationEnabled` 的 `maxTouchPoints` 必须落在 1..16；写 0 被拒，
   报错文案却是「Touch points must be between 1 and 16」（看起来像上一条 touchEnd 出错）。
