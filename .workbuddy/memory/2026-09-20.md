## 1. Vite 报 `@opendaw/*` 无法解析 —— 已修

用户贴的错误：dev server 启动即报
`The following dependencies are imported but could not be resolved: @opendaw/lib-std / lib-jsx / lib-runtime / lib-dom
(imported by .../OpenDWA/openDAW-main/.../main.tsx)`。

**根因**：Vite 5.1 起 `optimizeDeps.entries` 默认用宽松 glob，会**扫描 root 下所有源文件**；
仓库根躺着 `OpenDWA/`（288MB / 1770 个 .ts/.tsx 的完整外来项目），它的 `main.tsx`
引用没安装的 `@opendaw/lib-*`，扫描阶段就把依赖优化打断。

**修法**（`vite.config.ts`）：
- `optimizeDeps.entries` **显式列出** `index.html` + `scripts/probe-*/**/*.html`（探针页不在预构建里
  会在探针跑到一半「发现新依赖 → 整页 reload」，表现为随机失败）；
- `server.watch.ignored` 排掉 `OpenDWA/` / `dist/` / `outputs/`；
- 第三方引擎包进 `optimizeDeps.include`，避免点选时才预构建 → 整页 reload 打断试听。

效果：启动 2.87s → **1.03s**，且不再报错。

## 2. 合并第二个项目（SoundTouchJS）的效果，让用户选变调方式

`@audio/shift`（5 个）此前已接入；本次把 **SoundTouchJS**（`@soundtouchjs/core` 2.1.1 +
`@soundtouchjs/stretch-phase-vocoder` 2.1.1，MPL-2.0）也并进来，新增 3 个引擎：

| id | 标签 | 是什么 |
|---|---|---|
| `st-wsola` | ST-WSOLA | 出厂链路：WSOLA + **Lanczos** 插值 |
| `st-long` | ST-长窗 | 同上但分析窗拉长到 120ms / 搜索窗 25ms |
| `st-pvoc` | ST-声码器 | 伸缩级换成**相位声码器**（算法族与颗粒拼接完全不同） |

新增文件：`src/engine/soundtouch-engine.ts`（离线驱动 + 3 个导出）。
`external-shift.ts` 加 `EngineFamily` 字段与 3 条 meta + 3 条 loader。

**接进来的三个坑**（都在 `soundtouch-engine.ts` 里注释了）：
1. `SampleBuffer` 是**立体声交错**（每帧 L,R）→ 单声道要复制成 L=R；
2. 只设 `st.pitch = ratio` 即可，内部会派生 `_rate`/`_tempo` 并**自动交换串联顺序**，
   别自己拼两段式；
3. **必须尾部补静音**（`PAD_SEC=0.3`）再按输入帧数裁回 —— 输入喂完后 `process()` 不吐残余、
   库里也没有 `flush()`，实测 0.720s 的源出 0.630s（**尾巴被静默截掉 12.5%**）。
   补静音后所有引擎输出时长精确等于源。
   → 通用教训：**流式引擎接进同步内核时，先验「时长契约」，别只看波形好不好听。**

另：库内**只注册了 `'lanczos'`**，写 `strategy: 'linear'` 会抛
`Unknown interpolation strategy id "linear"` —— d.ts 注释里 `@defaultValue 'linear'` 是**错的**。

**UI 分组**：9 个 chip 里有两组名字高度相似（`lib-WSOLA` / `ST-WSOLA`），不分组看起来像重复项。
`EnginePicker.tsx` 按 `EngineFamily` 分组渲染（组标签 `@audio/shift` / `SoundTouchJS` + 一根细竖线）。
默认仍停在「我们的 PSOLA」→ **零行为变化**，只有用户显式点选才走外部路径。

**实测 HNR（dB）**：大降调时 `st-long` 明显最好（−12 半音：12.04 vs 我们 2.02）；
但质心只有源的一半（2200 vs 3855）→ 听感**偏闷**，是它换「干净」的代价。

**打包体积**：`soundtouch-engine` 独立 chunk = **33.9KB / gzip 9.1KB**，不进首屏
（第三方库必须走**字面量** `import()`，Vite 才做静态分析并切 chunk）。

## 8. 「变调引擎切换不稳健」—— 用户报的问题，查实并修了四处

用户只说了一句「那个变调引擎切换不稳健」。按项目规矩**先用探针把状态量出来**，
不要靠读代码猜。写了个观测口（`probe-palette.html` 的 `window.__engine()`）同时读
「用户选了谁」与「播放时实际会不会走外部路径」，一测就复现了：

> 刷新页面后：chip 仍高亮「ST-长窗」(`choice='st-long'`)，但 `shiftReady=false`、
> `loading=[]`、`willUseExternal=false` —— **连加载都没发起，播放静默走 wasm**。

这就是「不稳健」的根：**「选中了谁」与「那个库真的能用了吗」是两件独立的事**。
前者活在 localStorage 里能过刷新，后者只是模块内存；而 `sample-player.ts` 第 408 行
只认 `getActiveShift()`，为 null 时整个外部分支被**静默**跳过 —— 面板却依然高亮着
用户选的那个引擎。用户看到的现象就是「有时生效有时不生效」。

修了四处：

1. **启动即自愈**（`external-shift.ts` 末尾 `void restoreEngine()`）。
   放在**模块级**而不是某个组件的 `useEffect`：`sample-player.ts` 静态 import 了该模块，
   所以任何入口启动都会走到，不依赖「这一会话打开过装配面板」——
   否则「从导出对话框直接导出」会拿 wasm 渲出来，正是最该避免的那种不一致。
2. **`pick` 允许重试**：早退条件从 `next === choice` 改成 `next === choice && ready`。
   刷新后「选中了但没加载」时再点一下必须能重试，否则用户没有任何办法救回来
   （旧实现在这里直接 `return` → 「点了没反应」）。
3. **切换要等变速内核就绪**：旧代码 `void ensureStretchReady()`（不 await）然后就
   `setEngineChoice` + 重放 → τ≠1 时切完的**第一声**永远还是旧引擎，第二声才对。
   改成 `await`，并把「choice 翻过去的那一刻 stretch 必定已就绪」写成了探针不变量。
4. **界面不许骗人**：新增 `getEngineStatus()` / `getEffectiveEngine()`，
   chip 高亮仍表示「用户的选择」，但下面那行说明**始终描述正在发生的事**，
   未就绪时明说「此刻听到的仍是我们的 PSOLA」/「点一下可重试」。
   组件上新加 `data-engine-effective` / `data-engine-status` / `data-engine-stretch`
   三个钩子，让「界面有没有说谎」可以被断言。

顺带把 `busy` 的**同步**影子（`busyRef`）补上 —— `setBusy` 不是同步生效的，而 `pick`
里有 `await`，同一帧连点两个 chip 会双双越过互斥锁。

探针第 8 节 10 条钉住，全套 **55/55 通过**（修前 46/48）。

### 引擎本身是干净的（另一条排查线，结论：无需修）

担心「某个引擎在某些素材上抛异常 → 被 catch 后静默回退 wasm」，写了
`.workbuddy/tmp/libsurvey/probe-robust.mjs`：8 个引擎 × **全部 41 个素材**，
查抛异常 / 输出时长违约 / **疑似空转**（输出与输入归一化互相关 >0.99）/ 电平偏离 >6dB。

结果全零：**没有一个引擎抛异常、没有一个时长违约、没有空转、电平差都在 ±6dB 内**
（源 0.138 vs 各引擎 0.135~0.138）。→ 「不稳健」不是引擎的锅，纯粹是上面那套切换状态机。

### 实测：先建判据，再接线

写 `.workbuddy/tmp/libsurvey/probe-all15.mjs`（robust / marker / detail 三模式）。
**先发现一个陷阱**：探针目录下藏着一份 `node_modules`，`shift-transient`/`shift-delay`
会解析到**旧版本** —— 实测会和 App 实际打包的版本对不上。已 `mv` 成 `.BAK-*`。

**19 对象 × 41 素材**：零抛异常 / 零时长违约 / 零空转；电平偏离只有
`paulstretch`(3) 与 `ola`(4)。稳健性没有任何问题。

**关键发现（−12 半音，我们只有 2.02）**：
`st-long` 12.04、**`delay` 10.40**、`st-wsola` 9.95、`st-pvoc` 8.88、`sample` 8.65、
`wsola` 8.62、`hpss` 7.19 …… 而 `phaseLock`/`transient`/`hybrid` 只有 **0.91**（比我们还差）。
`delay`（延时线和声器）在 −8 档也已 11.26 > 我们 9.07，是个此前完全没被注意到的候选。
质心普遍掉到源的一半 → 全都**偏闷**，这是「干净」的代价。

**耗时**：我们是最慢的一组（中位 180~270ms），多数第三方 10~50ms。选型要计入点击延迟。

### 两个判据：为「指标全绿但东西坏了」准备的

`@audio/shift-sample` 是播放速率式纯重采样，自述 `output duration = input_length / ratio`。
它**通过所有常规判据**：数组长度完全相等、电平对、f0 也确实降了 ——
只有内容被按 ratio 压过，降调时**尾巴整段丢掉**。常规指标一个都发现不了。

1. **尾巴标记测试（决定性）**：造「音−静音−音」三段合成信号，量
   `输出尾 25% 能量 / 头 25% 能量`。正经变调器 ≈1.0，播放速率型 ≈0.0。
   实测 0.6216 与 0.5 **两个比例**：只有 `sample` 是 **0.000**，其余 18 个 0.95~1.10。
   **必须同时跑正弦与噪声两版**：`lpc`/`ola` 在**纯正弦**上会退化（AR 包络就是那个分音），
   只用正弦会冤枉它们（`lpc` 正弦 0.124 / 噪声 0.952）。
2. **包络时间比 `a`（辅助，极易误读）**：把输出 RMS 包络与「源包络按 a 倍重采样」比。
   **两个坑**：① 不能只看 argmax —— 包络平滑，峰值很平，`psola`/`wsola`/`delay`/`lpc`
   的 argmax 都落在 0.78~0.90 而 `a=1` 处只差 0.00~0.03，按 argmax 报会**全部误判**；
   ② 增益大 ≠ 真被改 —— ST 三个在 −12 档增益涨到 +0.28~0.46，但尾巴标记证明
   它们**完全没丢内容**（1.005/1.007/1.084），最可能是流水线内部延迟被无 lag 的
   scale 拟合吸收成了「轻微压缩」。**硬判据永远用尾巴标记。**

## 10. 用户报「你是不是把某个移除了」→ 真凶是选择器裁掉了整组

### 先回答「有没有被移除」：没有

用户怀疑少接了一个引擎。先查 registry 再查运行时，两层都是完整的：

- `@audio/shift@1.1.4` 的 `dependencies` = **恰好 15 个算法子包**（`index.js` 里那个

- 新增探针第 10 节：把 18 个 id **逐个点一遍**，要求 `shiftReady && !failed &&

### 真凶：`max-h-[7.5rem]` 把 SoundTouchJS 整组推到可视区外

`EnginePicker` 的分组容器写死了 `max-h-[7.5rem]`（120px）+ `overflow-y-auto`，
理由是「18 个 chip 平铺会把面板顶得老高」—— 但那个上限是按**宽**布局算的（四组各一行 ≈ 76px）。

而 `NotePalette` 的内容区是 `flex-col lg:flex-row`：**视口 ≥1024px 时切成两列**，
选择器那一列只有 **244px 宽** → chips 换行后四组共需 **157px** →
`overflow-y-auto` 把最后整组（`st-wsola` / `st-long` / `st-pvoc`）推到滚动区之外。
界面上看就是「那几个引擎被删掉了」。

量法（`.workbuddy/tmp/measure-picker-clip.mjs`，跨 4 个视口）：

| 视口 | 选择器宽 | clientH | scrollH | 结果 |
|---|---:|---:|---:|---|
| 1500 / 1280 / 1100 | 244 | 120 | 157 | ⚠ 溢出 37px，ST 组起点 121 > 底边 120 |
| 900 | 486 | 77 | 77 | ✓ 不溢出 |

- 结果：**64/64 通过**，`npm run typecheck` 0 错。


## 11. 用户报「有些时候素材无声 / 变调后无声」+「变调 / 浏览素材变的很卡」

两条都在同一天报出，最后的结论是**两个独立根因**，不是一个。

### 11.1 卡：降级链断在「第二次调用要重算」上

先量，不猜。新写 `.workbuddy/tmp/libsurvey/probe-silence-lag.mjs`
（与 App 的调用方式一致：**立体声**喂进去，之前的探针只喂单声道）：

- 41 素材 × 19 引擎 × −12 半音的**中位耗时**：我们 mode1 **283ms**，
  第三方 hybrid 246 / ST-声码器 278 / psola 266 / hpss 165 / lpc 116 / wsola 104，
  快的一档 18~56ms。
  → **我们自己也不快**，所以「卡」不是「第三方比我们慢」，而是
  **谁只付一次**：`rush/transform.ts` 有 WeakMap 缓存，第三方路径**一个缓存都没有**。
- 放大环节：`exporter.ts` / `take-player.ts` 是**逐事件**调 `playSample` 的，
  一个 200 事件的 take = 200 次全量变换，全同步跑在主线程上。

改了三处（`sample-player.ts`）：
1. `transformByExternalCached`：`WeakMap<AudioBuffer, Map<engine|pitch|time, buffer>>`，
   每源最多 8 条 LRU。键带**引擎 id**（换引擎必须重算，否则「切了引擎声音没变」）。
2. **空变换短路**：`|pitch−1|<1e-4 && |τ−1|<1e-4` 时根本不进引擎。
   wasm 那一侧本来就有这个短路，第三方没有 —— 而 ratio=1 是 App 里**最常见**的档
   （autoTune 关掉又没手动移调时）。
3. 新增 `external-shift.ts::getActiveEngineId()`（判据与 `getActiveShift()` 逐字一致），
   给缓存键用。

### 11.2 无声：根因是移调增量**没有上限**

`palette-reducer.ts` 的 `AdjustPitch` 只做了 `state + action.delta`，
τ 有 `clampTau`、半音什么都没有（注释还写着「pitch 无夹取」）。而
`Shift+↑` 是**按住连发**的（`NotePalette` 把 `e.repeat` 当 `silent` 传进 `nudgePitch`）
→ 按住两三秒就能到 ±60。实测那些档位（龙.001 / 立体声）：

| 档位 | ratio | 谁坏 | 现象 |
|---|---:|---|---|
| −60 半音 | 1/32 | `shift-sample` | 输出 **−46.3dB** = 听不见 |
| −60 半音 | 1/32 | ST 三个 | **2900~5650ms**（0.72s 的素材！） |
| +36 半音 | 8 | `ST-声码器` | 长度 0.704×、电平 +16.3dB、**峰值 31.96** |
| +48 半音 | 16 | `ST-声码器` | 长度 0.352×、电平 +14.3dB |
| +60 半音 | 32 | `ST-声码器` | 长度 0.176×、峰值 11.48 |

而且这个坏值会随 Apply **写进事件并持久化** → 之后回放/导出永远是坏的，
看上去就是「这条素材坏了」。用户那句「有些时候素材无声」正是这个。

修：新增 `src/model/pitch-limits.ts`（`MAX_SEMITONE_SHIFT = 24` +

（把上线前存下的 ±60 也收掉）、`NotePalette::nudgePitch`（**试听与提交必须逐位相同**，
否则会出现「听到 25 半音、提交 24 半音」）。
为什么是 ±24：不是新发明的数，`engine/pitch.ts::sampleSemitonesAtPitch`
早就在用它当「自动音高像检测失败」的界 —— 把那条界也用到这里，而不是另立一个。

### 11.3 出口验收：给「合法但坏」的输出加判据

降级链靠**异常**推进，而第三方库「返回合法音频但内容是坏的」不会抛异常。

本轮第一次复跑，探针在**第 1 节**就炸：

TypeError: window.__rows is not a function

这个报错完全误导人（指向探针自己的取数函数）。真因是**页面根本没执行**。

2. **⛔ `load()` 的 12s 上限对 vite 冷启动太短。**

   tfjs 的 `register_all_kernels` chunk 就有 1.8MB），期间还可能整页 reload。

   → 已按 URL 白名单排掉。**假红比不检查更坏**：它会训练人忽略这条断言。

**另外**：`load()` 现在超时**当场抛错并打印导航目标/页面异常/页面控制台**，
不再静默往下走（否则永远炸在 `__rows` 上，与真因无关）。

**通用教训**：探针类工具的失败经常**报错位置与真因相距很远**。
凡是「取数函数不存在」这种报错，先怀疑**页面是否真的执行了**（导航/代理/模块加载），

## 13. 装配面板：调音目标不再要求先按 Enter（用户报的细节）

**用户原话**：「当 Shift+A 的是已经有装配素材的音符块，那就不应该视为没有选择素材 ——
正常调音调的是当前音符的素材；除非按下 Enter 选其他的素材了，那就走正常的链路。」

### 13.1 真凶：把「有目标」等同于「用户按过 Enter」

旧闸门写的是 `if (armedId) return true;`（`NotePalette` 的 `guardArmed`）。
`armedId` 只由 Enter / 单击设置 —— 于是**已经装好素材**的音符（Shift+A 进来最常见的情形）
按 Shift+↑ 会被拦下并提示「还没有选择素材 请按Enter选择素材」：明明有素材，却被告知没选素材。

**修法**：把两个事实拆开（都是「目标」，但来源不同）

| | 含义 | 来源 | 随光标变？ |
|---|---|---|---|
| `armedId` | 用户**本次明确选中**的候选（可能是在换素材） | Enter / 单击 | 否 |
| `placedId` | 这条音符**本来就装着的**素材 | 打开面板时的 `effectiveSampleId` | **否**（事实） |

- `tuneTargetId(state)` = `armedId ?? placedId` → 调音 / 变速 / 试听 / 音高读数。
  **不含光标兜底**（`staged.candidateId` 会被鼠标悬停带走，拿它当目标就会改到「路过的那一行」）。
  只有两者都空才拦下 —— 这才是唯一该弹「还没有选择素材」的情形。
- `resolveTargetId(state)` = `tuneTargetId ?? staged.candidateId` → **只给「应用」**，
  保留既有「音符没装素材时按光标行落」的契约。
- **Enter 刻意仍只看光标行**：Enter 的语义是「我要这一行」（主动指向）。
  若它也认 `placedId`，「第一次回车只选中、第二次才提交」的双保险会在
  光标恰好停在已装配素材上时失效 —— 探针第 6 节 C 组专门钉这条。

### 13.2 连带修正（不改就会留下「改了 A 提交 B」这类隐形错）

- `previewWith` / `displaySemitones` / `PitchDisplay` / `canApply` / `applyTargetName`
  全部改用解析后的目标；`nudgeStretch` 的步进基准从 `armedSample.durationSec` 换成
  **目标素材的时长** —— 否则目标来自 `placedId` 时基准是 0，变速整组被按死（Shift+→ 没反应）。
- 组件级 `armed` 改名 `tunable`（它已不等于「按过 Enter」）；探针钩子
  `data-armed` → **`data-tunable`**，并新增 **`data-tune-target`**（目标的 id）。
  后者是关键：**「控件亮着」不等于「改对了素材」**，只有读实际目标 id 才能发现
  「目标悄悄退化成光标行」。
- 页脚提示从两态变**三态**：无可调目标 / 已装配未改选（「调音作用在 <名称>（当前装配）」）/ 已选中。

### 13.3 验证

- **单测**：`palette-reducer.test.ts` 58 → **78**（新增 20 条：placedId 的成立条件、
  `tuneTargetId` 优先级与「绝不回落光标」、`resolveTargetId` 的兜底边界、
  双保险不因 placedId 破功）。全量 208 passed / 2 failed（都在既有的
  `prototype-reverb.test.ts`，与本次无关）。
- **探针** `_probe-palette.mjs`：**79 → 91/91**。第 6 节重写成四组，靠探针页新增的
  **`?eff=p1|none`** 开关把两种情形分开钉：
  - **A** 已装配 → 调音直接可用、不按 Enter 就能 Shift+↑/→、目标 = p1、
    光标移开后目标不变、点「应用」提交 p1 + Δ；
  - **B** 回车改选 → 目标切到 p2、二次回车提交 p2；
  - **C** 光标停在已装配素材上时，首次回车仍只「选中」（双保险不破功）；
  - **D** 未装配（`?eff=none`）→ 才禁用 + 提示 + 数值不动 + 回车后解禁。
  第 5 节同步扩成三态文案断言（只测首尾两态会让中间态静默缺失）。
- `typecheck` 0 error。

### 13.4 顺手修掉一条探针假红（与本次功能无关）

第 8 节「刷新后变速内核也已就绪」轮询的是 `!after.shiftReady`，而
`restoreEngine()` 是**两段顺序 await**（先变调后变速）→ `shiftReady` 变 true 时
变速**才刚开始加载**，取样必然可能读到 `stretchReady=false`。
判据：红的那一刻紧接着的「点选 ST-WSOLA」立刻是 ready。
**修法**：轮询条件改成 `shiftReady && stretchReady`（预算 6s，真失败仍会报红）。
**通用教训**：凡「等 A 就绪 → 断言 B 也就绪」，先问 A 与 B 是不是同一段 await 里设的。

## 14. 用户报「调音只响一点点」+「手感粘滞」→ 时序问题（不是代码对错）

用户两句话：「有时候我在调音的时候 声音响了 但 只响一点点，这个情况发生在 Shift+A
装配面板的时候；期望是每一次调音都能响完」「我发现现在调音会有一点点粘滞的手感，
调查一下 是调音生成的真实时间 还是在某些地方出现了性能问题」。

两句都不是「代码对不对」而是**时序**，所以先建测量手段再改代码：

### 14.2 三个根因

1. **掐得太早**（「只响一点点」）：`previewWith` 在入口就 `stop()` 上一段，而下一段的
   整段变换是**同步**的（实测 1.0s 素材 580ms）→ 「新的还没算完，旧的就先掐了」。
   于是每段只活到下一次按键进来为止，段间还留 558~590ms 空档。
2. **同步变换挤在按键处理里**（「粘滞」）：变换跑在事件处理里 → React 的提交虽在末尾，
   **绘制**要等主线程空出来 → 按下后数字半天不出现、界面冻 ~0.6s。
   按键重复把它放大 N 倍（5 次连按 = 5 × ~600ms）。
3. **起播时刻取得太早**（潜在无声）：`when` 在变换**之前**取 → 整条包络被排到过去。
   `__envStale` 直接实测：`when` 落后 1200ms 时 1.0s 素材渲出来 **RMS=0.00004**
   （落后 100/600ms 时分别是 0.3555/0.3561）→ **落后量超过素材长度就是一点声音都没有**。
   本项目实测落后量是素材长度的 0.33~0.58 倍，所以**暂时**没撞到；
   但第三方引擎更慢（444/483ms，ST 系还有秒级的）→ 留着一颗雷。

### 14.3 修法（四改，都在试听路径上）

| 改 | 位置 | 内容 |
|---|---|---|
| ① 起播时刻后移 | `sample-player.ts` | `startAt = max(requestedWhen, ctx.currentTime)`，**变换之后**才落定；包络整条按 `startAt` 排 |
| ② 交棒式停播 | `sample-player.ts` | 新增 `options.replacePrevious`，在 `src.start()` 前一刻才停上一段 |
| ③ 先画后算 | `NotePalette.tsx` | `yieldToPaint()`（`rAF → setTimeout(0)`，80ms 兜底）后再调 `playSample` |
| ④ 重复不试听 | `NotePalette.tsx` | `e.repeat` 只 dispatch；值落定（keyup，兜底 160ms 防抖）后试听一次 |

顺带：`PlayingSample.stop()` 增加「已自然结束 = no-op」判据（②之后会经常对已播完的句柄
调 stop，原来会抛 InvalidState 被 catch 成 warn 刷日志；噪声日志比不检查更坏）。

### 14.5 回答用户的第二个问题：「是生成的真实时间，还是性能问题？」

两者都有，分开说：

- **是真实计算量**：`__scaleShift` 实测耗时对素材长度**线性** —— 0.25/0.5/1/2s 分别
  111/221/535/1155ms（446/442/535/577 ms 每秒素材，8× 长度范围内比值 **1.30**）。
  没有超线性，不是算法问题，就是每秒素材约 0.45~0.58s 的计算。
- **但有两处放大器**（这才是「粘滞」的主因，已修）：把变换放进按键处理（×N 次重复）、
  以及让数值等变换算完才画。
- **残留（已量化、未修）**：一次试听仍会让主线程冻 **~500~900ms**（长任务实测 867ms）。
  消掉它要把变换搬进 Worker，会牵动 `exporter` / `take-player` 的同步调度契约 ——
  属独立一轮，需要用户先点头。

### 14.6 测的时候踩的四个坑（都是「测出来是假的」）

1. 参量事件等 `src.connect(env)` 才登记 → 整条包络事件表**全漏**，算出来的增益是
   「没有自动化 = 1」，把 bug 掩盖成正常。（`playSample` 是**先排包络、后 connect**）
2. `__tune` 把事件 dispatch 在 `[role="dialog"]`（`onKeyDown` 容器的**祖先**）上 →
   0 次试听、数值纹丝不动。而「最多两次」这种**上界断言照样报绿** ——
   已给上界断言补上下界（`length >= 1`）。
3. 增益取样点取在「起播瞬间」→ 读到的是起音斜坡起点 0.0001（设计如此），
   反而把**坏掉**的情形读成 1，**指标方向是反的**。改取 `startEff + 20ms`。
4. `__envStale` 用 `when = currentTime - pastMs/1000`，**AudioParam 不接受负时间** →
   600/1200ms 两档全抛 RangeError，看起来像「落后多了就崩」。先等时钟走够。

**通用教训**（已进 `REF-frontend.md` §6.2）：探针报绿之前先问「它测的到底是不是那件事」——
上界断言会被「什么都没发生」满足，取样点选错会让指标方向反过来。

### 15.1 但日志里确实暴露了一个**真 bug**：那句报错指错了地方

`new Worker(url)` 的脚本加载是**异步**的，失败时浏览器给的 `ErrorEvent` 里
`message` 常常是**空串**（真信息在 `filename`/`lineno`，或什么都没有）。
旧代码是：

```ts
reject(new Error(e.message || '音高 worker 异常退出'))
```

→ 所有线索被丢掉，只剩一句把「**进程没了**」说成「**音高算法坏了**」的兜底话。
按它的指向会一路查 DSP / 模型 / wasm，而真因在几百米外的进程列表里。

**新规矩**（已写进 `MEMORY.md §D`）：兜底文案不许是「出了个错」，
必须是「最可能是什么 + 下一步查哪儿」。

### 15.2 修了四处（`src/engine/pitch-worker-health.ts` 新文件 + 三处改动）

1. **失败分类** `classifyWorkerFailure`：`script_load`（拿不到脚本 → 重生无用，先修环境）
   / `runtime`（跑起来后抛错 → 重生有效）/ `unknown`（没线索，给最可能的原因 + 查哪儿）。
2. **重生冷却窗** `shouldSpawnWorker`（2s）：旧行为是 `worker = null` 之后
   **每个请求都 `new Worker`** 一次 —— 用户日志里那四条同样的报错就是这么来的，
   且每条都要等一次网络失败。
3. **`onerror` 只摘自己那一个实例**：旧实现无条件 `worker?.terminate(); worker = null;`，
   若此刻 `worker` 已指向重生后的新实例，会把好的那个一起干掉（表现为「时好时坏」）。
4. **worker 不可用不许连累 YIN**：`PitchWorkerUnavailableError` 让
   `getSamplePitchHzDetailed` 区分「这条请求出错」（照旧抛）与「worker 整个没了」
   （→ 主线程 JS 应急退路），不然故障态下**所有**素材都显示「未检出音高」。

UI 侧：`PitchWorkerStatus` 加第三态 `'unavailable'`，并加 `getPitchWorkerStatus()`
（组件挂载晚于事件时必须取初值，否则从 `'ready'` 起步 = 谎报）。混进 `'loading_model'`
的代价是 worker 死掉时 UI **永远**停在「首次加载 AI 模型…」—— 把「这里坏了」显示成「再等等」。

### 15.3 ⚠️ 一个不许被推断的数字（差点写错）

我原本在注释里写「主线程跑 JS YIN 是**毫秒级**」—— 那是**猜的**。
补了 `__yinCost` 实测：**单次 307 / 293 / 295 ms**（1.0s @48k）。
「有界」（`maxFrames: 24`，与素材长度无关）**不等于**「很小」。

结论不变（仍然保留这条退路），但**理由换了**：不是「它很快」，
而是「① 触发时机很稀（只在目标素材/检测器/参数变化时，**不跟按键重复跑**）
② 对照组是『所有素材都未检出』」。并且明确写上 ⛔ **别让它变常态路径**。

### 15.4 一次**假绿**（值得单独记）

复现「worker 起不来」时，第一版实现是：同一页面上先跑正对照，再 `__breakWorker(true)`。
结果三项接口**全绿**，日志却是 `spawns=0 / status=ready / kind=undefined` —— 全是默认值。

**原因**：`pitch-async` 的 worker 是**单例**，而它的「活着」**不依赖 dev server**
（模块早就在内存里）。所以后续请求全部命中那个真 worker（连 AI 都照跑，返回 185.0Hz），
`new Worker` 那条路**根本没被走到**。

**修正**：加 `?npw=1`，在页面模块里、`createRoot(...).render()` **之前**换掉全局 `Worker`，
并**重新加载页面** → 全新模块状态 = 全新的「还没建过 worker」。
桩只拦音高 worker（`sample-player` 的 `audio-worker` 要放行，否则整个面板解不出音频），
且 fire 一个**四字段全空**的 ErrorEvent（= 浏览器「脚本拿不到」的形态）。
详见 `REF-frontend.md §7`。

## §18 UI 现代化 + 半音 / 音域 —— 设计讨论（**只聊天，未动一行代码**）

用户提四件事：UI 轻微重构 / 音名统一为 C D E F G A B / 加半音（带开关）/ 音域从 21 扩到
FL 式 C0–C8 并可缩放到只看几个八度。以下是**已向用户陈述的判断**，等他拍板再动。

### UI：设计系统没问题，「显得旧」另有其因
`tokens.css` 是 Apple Neutral 暗色体系（四级面阶梯、单一 systemBlue、零色偏灰、
发丝线代替阴影、圆角 4/6/10），三条戒律「静/层/手」写得很清楚 —— **不要**换配色 /
加渐变 / 加毛玻璃，那会毁掉用户自己打 9.8 分的交互手感。真因是：
1. **字号太小**：`--fs-body 12.5px`、`--fs-micro 9px`（9px 在 1080p 上就是糊的）。
2. **制作台顶部叠了三层控件条**（模式切换 / 录制片段 / 传送栏）→ 竖向空间被吃、卷帘变矮。
3. **符号控件无语义**：`−` `+` 紧挨 `行−` `行+`，要试两遍才知道哪个是时间缩放、哪个是行高。
4. **素材箱空态自相矛盾**：虚线拖拽框很大 + 右上「上传」很小，却是同一个动作。
→ 「轻微重构」= **间距与层级**的活，不是皮肤的活。

### 音名统一：先定八度约定
现在有**两份唱名实现**（`store.ts::defaultKeyLabel` 用 `do'`、`geometry.ts::laneLabel`
用 `do′` —— 连撇号都不是同一字符），另有 `midiNoteName`（C4）与装配面板的「C4 60」。
统一到 C/D/E 是**减重复**，赞成。
⛔ 但必须先定：**C4=60（代码现状 / 科学音高 / .mid 标准）还是 C5=60（FL 习惯）**。
用户说的「第一个添加的是 C3」在两种约定下差一个八度（MIDI 48 vs 36）。建议保留 C4=60。

### ⛔ 半音开关的真正难点 = 迁移语义，不是画 12 列
现在 `keyIndex` 是**位置**，音高由 `pitchOfLane` **推导** → 换算表一换，「下标含义」就变。
按新表重算会让已装配素材集体跑调（下标 1 D→C#、2 E→D、3 F→D#、4 G→E，最多 −4 半音）。
三条路：按位置重算（❌）/ **按音高守恒（✅推荐：插黑键、素材跟音名走、听感零变化）** /
已有内容时禁切。
→ 按音高守恒的**前提**：Key 的身份要从「下标」升级为「音高」。
**好消息**：`TakeEvent` 早已有独立的 `pitch` 字段（`types.ts:78-81`），路铺了一半。

### 「一行 = 一个八度」
OFF 时今天已成立（`KeyLayout` COLS=7）。ON 时一行要装 12 个半音 → 撞死写死的「绝不超
7 键/行」，且手机 12×56 = 672px 必然横滚。
→ 建议拆成两种几何：**OFF 保持 7 列；ON 改用钢琴几何 = 7 白键格 + 黑键半高骑缝**。
它恰好与键盘映射一一对应（Z 行白键 / S D G H J 黑键 / Q 行下一个八度），
而且「一个八度仍然是一行」这条规则保住了。

### 好消息：卷帘**已经**能干这件事
`useRollController` 现有 Ctrl/⌘+滚轮 = 时间缩放、**Alt+滚轮 = 行高缩放**（均锚定指针）、
双指捏合、拖音符换行；`rowH` 支持 9–72px、`sy` 纵向滚动齐全。
所以「缩放到只看几个八度」**几乎不用写新代码** —— 真正的改动只有一处深改：
把「卷帘纵轴 = keyCount 个键位」换成「纵轴 = C0–C8 音高域」。

### 两个连带效应（别漏）
1. `midi-import.ts:38` 的 `raw % keyCount` **循环折叠** → 音域变宽后可降级为 `clamp`；
   现在超出键域的 MIDI 音会被折回，等于随机移调，改了反而更对。
2. `model/pitch-limits.ts::clampSemitoneDelta ±24` → 音域一宽，拖一个音符极易 >24 半音
   被静默截断。阈值要不要跟着放宽 = 第二个决定。

### 成本分级（给用户看的）
- 便宜：音名统一（两份唱名合一份）
- 中等：键位矩阵的半音开关 + 钢琴几何
- 贵但值得：Key 身份「下标 → 音高」+ 卷帘纵轴改音高域 —— 牵动
  `store / persistence / roll(geometry·renderer·controller) / palette-reducer / midi-import`

### 等用户拍板的 6 项
① 八度约定 C4=60 还是 C5=60 ② 开关迁移语义（推荐音高守恒）③ 音域上下限（C0–C8 / 88 键 / C1–C7）
④ 半音开启时的矩阵几何（推荐钢琴几何）⑤ 自动下一个音的阶梯到顶后怎么办（回绕 / 停住 / 提示）
⑥ 音名是否一律带八度数字，以及装配面板标题「装配第1首 · do · 第1度」改成什么。

### 新增：`src/model/pitch-map.ts` —— 键域与音高序列的**单一事实来源**
