# WASM DSP 质量门禁

本项目的人声变换内核是 Rust → `wasm32-unknown-unknown` 的 `hajimi_audio.wasm`，
源码在 `wasm/src/`。**任何 DSP 改动都必须用客观数字验收**，不能只靠「听起来好点了」——
听感回归一次只能听一段，而指标能一次覆盖 10 个用例并抓到改前改后的方向。

**但反过来也成立，而且是本技能最重要的一条规矩**：指标**只能排除，不能选优**。
「哪个更好听」必须由耳朵定；指标负责解释耳朵听到的东西。
本技能里那个被实听否决的 mode 3 就是反例 —— 每一项客观指标都变好，听感更差。
**耳朵说更差时，不要拿指标去反驳。**

## 为什么必须留改前产物

改前先存一份 wasm。否则改完只能说「现在是这样」，说不出「之前差在哪、这次修没修到」。
本项目已经出现过这种情况：一开始把「拉伸像放屁」归因到别处，存了基线才定位到
blend mask 建错了时基。

```bash
mkdir -p .wasm-cmp
cp wasm/target/wasm32-unknown-unknown/release/hajimi_audio.wasm .wasm-cmp/before.wasm
```

## 指标电池怎么看

`measure-psola.mjs`（变调/拉伸，`hajimi_tx_run`）：

- **四段 F0**：把输出切四段分别测基频，和期望值比。单测一段会漏掉「前半段对、后半段垮」。
  这一项就是当初发现「拉伸 mask 建在源时间轴」的那把尺子（改前 `只拉伸1.5x` 四段 = 200/200/66.7/133.3）。
- **最大音分误差**：应该 ≤0.5 音分。拉伸崩溃时是 1902 音分。
- **杂散 dBc**：源作为参照必须同列打印。低频杂散抬升 = 抖动/相位错乱。
- **周期 CV / 峰谷比**：抓 f0 速率的振幅调制（听成「颤 / 噗噗噗」）。用**周期对齐**的 RMS
  去量，不要用等间隔窗——等间隔窗会把基频本身的起伏算进去。
- **跳变峰**：相邻样本最大跳变。抓起音处的咔哒（源 ~1.3，坏的时候到 8.1）。
- **帧数（期望）**：时长守恒（`round(N * time)`）。

`measure-autotune.mjs`（自动修音，`hajimi_at_run`）：

- **稳态响度比**：修音后 RMS / 源 RMS，应 ≈1.00。这条最容易被忽略——缺局部增益匹配时
  升 5 半音会掉到 0.744（-2.6dB）。
- **颤音压平量**、**长清音段逐样本放行**、**④起音跳变峰**（无 onset anchor 时必抬升）。

### 咔哒/杂音专项：`scripts/_probe-clickcount.mjs`

用户报「爆音/杂音」时先跑这个。它**逐素材统计「比源多出来的离散发散点簇数」**：

```bash
node scripts/_probe-clickcount.mjs        # 41 真素材 × 13 档（含 ±5/±7/±9/±12、x1.4、x0.7、SOLA）
```

判据：`|Δ| > 8×median(|Δ|)` 的样点，间隔 <16 样本算同一簇 → 一簇 ≈ 一声咔哒。
**看「增簇中位 / 增簇最大」两列，而不是看绝对簇数** —— 真素材本身就有很多
辅音/呼吸造成的合法尖沿（源簇中位 42、最大 258），绝对值没有可比性。

两个关键读法：

1. **`恒等` 档必须全 0**。它是逐样本拷贝，增簇 ≠ 0 说明探针本身坏了。
2. **逐档扫参数轴，不要只测两点。** 本项目的 Σw floor 闸门 bug 只在
   ratio < 2/3（-7.02 半音）时触发，只测 ±5 或 ±12 都会给出错误的「没问题/全崩」结论；
   沿 ±5/±7/±9/±12 一扫，「增簇中位」是 1 / 11 / 30 / 24 —— **-7 处的台阶**就是根因所在。
   凡是「由几何条件决定是否触发」的缺陷，表现一定是**阶梯**，扫密一点就能看见转折点。

配套：`_probe-gain.mjs`（逐 10ms 帧的 `RMS(输出)/RMS(源)` 剖面 + 峰值增量），
`_probe-artifact.mjs <信号|素材名> <pitch> <time> <mode>`（全段找最陡跳变，
同时打印**同一输出时刻的源波形**，用来区分「忠实还原的瞬态」与「合成器造的爆音」——
这一步很关键，本项目曾把源自身的声门瞬态误判成尾部咔哒）。

### 沙沙/毛糙专项：`scripts/_probe-hnr.mjs`

「咔哒」是**离散尖沿**，「沙沙」是**宽带噪声**，两者机制不同，别用同一个探针。
沙沙用**逐帧周期同步平均 HNR**：

    h = 周期同步平均（谐波成分）      r = x - h（噪声成分）
    HNR = 20*log10(rms(h)/rms(r))     逐帧 40ms 算、取中位数

```bash
node scripts/_probe-hnr.mjs --selftest               # 先跑自检！见下
node scripts/_probe-hnr.mjs "龙.001" 0.6216 1.0 1    # 素材 pitch time mode
```

它会同时渲染并分析**三路**，并写 WAV 到 `public/_ab/` 供试听：
源 / 纯线性重采样 / 我们的 PSOLA。

**关键读法**：跟**同输出音高**的纯重采样比，不要只跟源比。
两者输出 f0 相同 → 估计器偏置相同 → 差值就是「颗粒合成**额外**加了多少噪」。
本项目实测：轻降调（-1.8 半音）PSOLA 不吃亏（+1.0dB），**-5 半音起单调加噪**，
-12 半音差近 10dB（PSOLA 1.98dB vs 重采样 11.73dB），周期性同步同时从 0.973 塌到 0.883。

**先看源自己的 HNR**。鬼畜素材本来就毛（龙 ≈10dB、米 ≈2dB）。源 HNR 只有个位数时，
「沙沙」很可能主要是**源的毛被忠实搬运**，而不是合成器造的 —— 这时该改的是素材或加去噪，
不是改内核。

### ⛔ 降调沙沙：试过「PSOLA + 谐波/噪声分离」（mode 3），**被实听否决、已撤下**

> **这一节留在这里主要是反面教材。** 结论：指标全绿、耳朵不接受 ——
> 用户原话「这个结果很糟糕，噪音变成另一种形式了」。默认链路已回到 `[1, 2]`。

#### ⛔⛔ 最重要的教训：客观指标只能**排除**，不能**选优**

mode 3 把降调侧的 HNR 从 9.07 提到 10.07 dB、HF 四个分档**全部压到源以下**、
质心比 0.995→0.930 —— **每一项都"更干净"**，但听感更差。原因是：

- **HNR 这类「周期可解释度」指标对"净化"的奖励是单调的**：纯正弦的 HNR = +∞。
  拿它当目标函数，最优点必然是「把人声做成合成器」。
- 抽掉的「非周期成分」不是脏东西，是**气声、辅音、微抖动** —— 让人声像人声的部分。
- 剩下的严格周期谐波在颗粒重排下变成**机械的嗡嗡/金属声**。这**不是新造的失真**，
  是 TD-PSOLA 的固有 artifact（文献名：**buzzyness**）—— 源里的气声本来掩盖着它，
  抽走气声 = 把它露出来。
- 残余只加回一半（β=0.5）且加在**原位频谱**上，而谐波已下移 8 个半音 →
  两层不再属于同一个声音，噪声变成「浮在低音上面的一层」。

**规矩**：DSP 改动不许只用客观指标验收。指标负责**解释耳朵听到的东西**并**排除**坏方案；
「哪个更好听」必须由耳朵定。反过来也成立：**耳朵说更差时，不要拿指标去反驳。**

#### 先做判决实验，别直接改内核

`scripts/_probe-hnsep.mjs`。**同一套 marks、同样的颗粒几何，只换喂进内核的内容**
（龙.001 @−8.23 半音）：

| 喂给内核的内容 | 输出 HNR | 周期性 |
|---|---|---|
| 原始素材 | 9.07 dB | 0.946 |
| **严格周期成分（谐波模板）** | **14.02 dB** | **0.991** |

周期成分喂进去比**源本身**（10.72dB）还干净 → **重叠相加对周期内容是干净的，
沙沙来自源里的非周期成分被颗粒重排。**
但**「所以要把非周期成分拿出去」这个推论是错的** —— 正确的是
「非周期成分要**跟着一起变调**，只是不走颗粒重排」。

#### 为什么只有降调受害 —— 收敛到**一个几何量** `A = 1/ratio`（= `advance/period`）

早期记录写的「两个机制」已合并。**先更正一条旧记录**：说「Σw 除法把噪声放大 ×5」**不准确**
——除法对信噪比是**中性**的（分子分母同比）。真实机制是：

- 接缝处**重叠占比** `1 − 1/(2A)`（占窗宽）：`A=1.33(.75)→33%`、`A=1.61(.62)→19%`、`A=2(.50)→**0%**`
- 接缝处**窗和** `Σw = 1 + cos(πA/2)`：`A=1.5 → 0.293`、`A=2 → 0` ——
  与 `psola.rs` 注释里那个「−7.02 半音台阶」逐字对上（`MIN_ENVELOPE=0.3` 的 floor 从这里起介入）
- 接缝处**相干增益** `|cos(π·frac(A))|`：重叠区里两颗颗粒读的是源里相隔 `frac(A)` 个周期的材料，
  所以**接缝相位失配恰好等于 A 的小数部分** —— `A=1.5 → 0`（**完全抵消**，这就是 −7 台阶的成因）、
  `A=1.6129 → 0.35`、`A=1.25 → 0.5`、`A=1 → 1`

三者叠加 = **相干抵消打在谐波上**、而**不相干叠加的噪声只按 √ 衰减（×0.707）**
→ 接缝的局部 SNR 相对中段下陷，且以**颗粒率（= 输出音高）做幅度调制** → 听成沙沙/嗡嗡。
越降越深：接缝占比上升、Σw 趋零；`A=2`（−12 半音）干脆没有重叠 = 一串孤立 Hann 包夹着静音。

**判据**：任何「降调变差」的假设，先算这三个数再动手。它们只依赖 `A = 1/ratio`，
所以能一眼判断某档是不是特殊坏点（`A=1.5` 是，`A=1` 不是）。

**推论（＝真正的修法入口，见下一节）**：恶化**全部来自 `A ≠ 1`**，
而 `A = 1/ratio` 只是因为**单段式让颗粒几何去承担变调**。

#### 实现要点

`wasm/src/psola.rs` 模块 E（`split_harmonic` / `analyse_at` / `noise_retention` / `table_at`）
+ `stretch.rs` 的 mode 3 分支。
（前端默认模式链**曾经**改成 `[3, 2]`，实听否决后已回到 `[1, 2]`；
mode 3 现在只有探针能走到。）

- 拆分：**按谐波频率做窗内正交相关**（4 个源周期的 Hann 窗），相位用逐样本周期积分
  （梯形法 ∫1/P，与合成侧同一套插值）。
- 合成：每分析点把谐波模型**预采样成一周期 512 点表**（`HN_TABLE`），
  每样本只做一次查表 + 线性插值 —— 省掉逐谐波 Chebyshev 递推与全部三角函数。
  mode 3 ≈ 0.92× mode 1 耗时（**不是瓶颈**；mode 1 本身就约 3× 实时，瓶颈是 YIN `track_pitch`）。
- 残余保留量 β 按 ratio 自适应：**启用线 `HN_ENABLE_MAX_RATIO = 0.89`（≈ −2 半音）以上
  完全不启用**（β=1.0、`split=false`，代码路径与 mode 1 完全相同）；
  0.62 → β=0.50（标定点，对齐真·PitchNet 的 HF 分档）；地板 0.35；单调不增。
- **增益匹配的参照物必须是谐波成分**（残余还没加回来时），否则会把「噪声被抽掉」
  误当电平损失补回来，净化量被自己抵消。
- 拆分只改「喂什么进颗粒内核 + 残余怎么加回」，下游的 Σw 归一 / 增益匹配 / blend 全部复用
  （把 `apply_planar` 拆成 `apply_planar_inner(.., split: bool)` 即可）。

**升调侧护栏**（用户明确说高音没问题，所以必须有回归钉住）：
`psola::tests::harmonic_mode_leaves_upshift_bit_exact` —— pitch = 1.0 / 2^(5/12) /
2^(7/12) / 2.0 **以及 `HN_ENABLE_MAX_RATIO` 本身**，都要与 mode 1 **逐字节相同**。改坏立刻红。

#### 实测（HF 分档相对源 dB = 2-4k / 4-8k / 8-16k）

| 素材 | HNR 源 | mode1 | mode3 | mode1 分档 | mode3 分档 | 质心比 |
|---|---|---|---|---|---|---|
| 龙.001 @−8.23 | 10.72 | 9.07 | **10.06** | +1.3/+0.6/+0.5 | **+0.4/−0.4/−0.5** | 0.995→**0.930** |
| 高北 @−12 | 4.97 | 1.41 | **5.75** | +0.2/+0.1/+0.5 | **−0.6/−0.8/−1.6** | 0.981→**0.914** |

#### ⛔ 坑 A：拆分**不能**用「±K 个周期的同步平均」

第一版用 ±K 周期**均匀滑动平均**当谐波模板，HNR 反而比原 PSOLA 差 1.33dB
（7.74 vs 9.07）。原因：13 抽头均匀平均的频响是 **Dirichlet 核**，
f0 估偏 1% 时**第 10 次谐波只剩 3.6% 增益** → 漏过去的高次谐波进了残差，
而残差**不做变调**，加回时与主路**同频不同相** → 打拍。
换成按谐波频率的正交相关后，残余 RMS 占比 0.42 → 0.32。
**判据**：任何「用平均/低通滤出谐波」的想法都要先问它对高次谐波的增益是多少；
周期同步平均的等效低通在分数周期误差下衰减得极快。

#### ⛔ 坑 B：判断「沙沙」**不能只看 HNR**，HNR 是标量、看不出方向

必须有**频谱分档侧写**。`scripts/_probe-pitchnet-ref.mjs` 拿真·PitchNet 导出
（`原型/PitchNet-master/导出测试.wav`）当参照，揭示的是：

| | 质心 | >4k 能量占比 | 分档相对源 |
|---|---|---|---|
| 源 | 1430 | 6.5% | — |
| 我们 mode 1 | **1556** | **8.7%** | — |
| 真·PitchNet 导出 | 983 | 3.8% | −2.0/−3.3/−2.8 |

→ 我们**在加噪声**，它在**减噪声**。这个方向信息 HNR 给不出来。
`_probe-hnsep.mjs` 里也内建同款 `spectral()`（质心 / >4k 占比 / 分档 dB）。

#### ⛔ 坑 C：**先测，再解释** —— 我自己的假设被一次测量否掉了

我原以为「残余里混着没吃干净的原音高谐波，加回去会跟变调后的谐波打拍」。
探针加了 `coherentAt(x, f0, sr)`（指定 f0 上的相干能量占比）实测：

| 对象 | 相干占比 |
|---|---|
| 源 @源 f0 420Hz | 0.410（参照） |
| **残余 @源 f0 420Hz** | **0.072** ← 假设不成立 |
| 残余 @输出 f0 261Hz | 0.117 |
| mode1 输出 @输出 f0 | 0.198 |
| mode3 输出 @输出 f0 | 0.180 |

残余确实是**宽带噪声**（0.07 对源的 0.41），不是锁在原音高上的谐波残留。
假设被否掉之后才去找真正的原因（buzzyness 被暴露出来）。
**把假设写成可测数字**，比把它写成一段解释性注释有价值得多。

#### ⛔ 坑 D：阈值常量必须与 ABI 入口参数**同精度**

`hajimi_tx_run` 的 pitch 是 **f32**，而 `HN_ENABLE_MAX_RATIO` 原本写 `f64 = 0.89`。
`0.89f32 = 0.88999998569…` **比 `0.89f64` 小一个 ULP** → 恰好传 0.89 的那档满足
`pitch < 线`，分离**提前一个 ULP 打开**，「启用线及以上逐样本相同」这条契约在 0.89 上失效
（探针实测差异 **0.61×源RMS**，且最大偏差落在**中段** = 系统性而非边缘毛刺）。

- 修法：常量改 `f32`、`noise_retention(ratio: f32)`、比较留在 f32；调用点抽成
  `hn_split_enabled(pitch: f32)` 以便测边界。
- 回归：`enable_line_is_exact_in_f32_abi_precision` 断言 `f32(0.89) == 常量` 且
  `!hn_split_enabled(f32(0.89))`。
- **为什么以前是绿的**：host 单测用 f64 字面量比较，永远测不到 ABI 的 f32 截断。
  **这个坑只有走 wasm 的探针能看见** —— 所以 `_probe-hnsep.mjs` 里也钉了一段【契约】。
- 通用规矩：**阈值/启用线的常量类型必须与 ABI 入口参数一致**，
  并且要有一条**从 ABI 那一侧取值**的回归测试。

#### 先记住：我们**已经是** TD-PSOLA —— 换名字不是改良

`TD` = time-domain，对立面是 FD-PSOLA / LP-PSOLA。`psola.rs` 的五条特征
（pitch mark 检测 + 互相关精修 / Hann 颗粒长度恒 2 个**分析**周期 / 以源 mark 为锚 /
以新间距排放 / Σw 归一）逐条就是 Moulines & Charpentier 的教科书 TD-PSOLA。
网上「改良 TD-PSOLA」的项目改的都是**参数与阶段划分**。用户问过这个，别从头再解释一遍。

#### ⛔ 已否决：两段式 TSM + 重采样（**不要再当成方案提出来**）

> **2026-09-19 与用户当面确认：代价不可接受 → 方案撤回，不落地。**
> 用户要的听感（PitchNet 那种「干净又舒服」）**恰恰来自共振峰不动** ——
> 那是神经声码器的 mel 不变、只换 F0。两段式正好把这一条丢掉，
> 等于拿一个缺陷换另一个缺陷，不是净改善；用户原话是「成本太高」。
> **后续除非目标明确是「怪物音」这类刻意改变音色的效果，否则不要再提。**

原理本身仍然成立（下面留着，是为了**解释 `A ≠ 1` 这条推论**，
以及将来万一要做音色变形时能直接用）：先做**时间伸缩**
（此阶段颗粒间距恒 = 分析周期 → `A ≡ 1`、重叠恒 50%、`Σw ≡ 1`，三条恶化同时消失），
再整体重采样 `ratio` 倍。变调与时长都对，但**没有任何一步让颗粒间距偏离分析周期**：

```
两段式 = apply_planar(x, sr, pitch=1, time = time*pitch)   // 复用现有内核，内核一行不改
         + resample(1/pitch)                               // 唯一的新代码
```

`wasm/src/` 里目前**没有任何重采样器**（`grep resample|sinc` 为空）—— 这是唯一要新写的部分，
O(n) 分数延迟滤波器，几 KB。**注意降调时是「压缩 + 升采样」，无混叠风险；
升调才是「拉伸 + 降采样」，必须带抗混叠**。

**代价（这是当初否决它的原因）**：重采样**把共振峰一起搬走**（×ratio）。
单段式 PSOLA 的卖点正是「保共振峰」；两段式会变成「降调 + 变厚/变闷」。
鬼畜素材常无所谓，但「同一个人换个音高」就不行。两头都要 → 得估谱包络做共振峰补偿
→ 那又滑回源-滤波器了。

#### 再下一站：源-滤波器（WORLD 系），不是在 PSOLA 上继续做波形级分离

**体积账（选型前必看，2026-09-19 实测）**：`public/hajimi_audio.wasm`
= 1142 KB raw / **483 KB gzip** / 379 KB brotli；`wasm/src/` 自有源码 ≈161 KB / 4387 行。
WORLD 全量估 **+130~280 KB gzip**（未实测，别当实测数字引用）。
且它假设**单一音源** —— 本项目的鬼畜素材带伴奏/音效，它的 F0 检测（DIO/Harvest）会出错
（本项目已记录「带伴奏时 F0 本来就不准」）；Harvest 还比我们的 YIN 慢一个量级。
真要上，更合理的是**只搬 CheapTrick + D4C，F0 继续用我们自己的 YIN**。

（另：探针试听 WAV **绝不能放 `public/`** —— Vite 会原样拷 `publicDir` 进构建，
曾被 62 个 WAV / 2.78 MB 打进 `dist/_ab`，比 wasm 本身还大，且 Vite 清 `dist` 时会触发
沙箱批量删除守卫直接构建失败。现统一写 `outputs/_ab/`（已 gitignore），
dev 下由 `vite.config.ts` 的 `serveProbeArtifacts()` 挂 `/_ab` 中间件提供。）

成熟做法是**按频带**估非周期性，合成时用谱包络**重新生成**噪声：

- **WORLD / D4C**（mmorise/World，BSD、无专利）：F0(DIO/Harvest) + 谱包络(CheapTrick) +
  **频带非周期性(D4C)**；周期包络 `α²·P_x`、非周期包络 `(1−α²)·P_x`。
  噪声是被谱包络**滤出来**的 → 天然跟着音高一起走，正是我们缺的那一环。
  已知坑与我们撞上的一样：V/UV 边界 + 齿音会把噪声误判成谐波 →
  「密集的全带齿音气流重合成后变成**刺耳的脉冲串**」。
- **Praat**（`Sound: Change pitch`）：PSOLA 教科书写法，pitch mark + 局部周期 2~4 倍窗长。
- **PyTSMod**：可读的 `tdpsola` / `hptsm` / `wsola` / `pv`，做 A/B 最省事。
- **Autotalent / TalentedHack**：现成的开源**修音**插件（PSOLA 系）。
- **sannawag/TD-PSOLA**：README 自己写明「<700 音分才基本无 artifact，位移越大越差，只对 voiced 成立」。
- **Rubber Band (R3)** / **signalsmith-stretch**：当代高质量对照。
- 失真文献：Longster 2003（Bournemouth）、SBrT'05 —— artifact 就叫 **buzzyness**；
  且「非周期段做 TSM 会给噪声引入周期性 → 金属声」。

**动手前先读这张表** —— 它会拦掉「在 PSOLA 上做全带波形相减」这类不成熟的思路。


### ⛔ 别拿 PitchNet 当「同算法对照组」—— 它默认根本不跑 PSOLA

说「PitchNet 干净、我们沙沙」之前必须先查这条，否则会追一个不存在的 bug。

`Source/Audio/SynthesisEngineType.h:19-26`：**只有 `#if JUCE_LINUX` 才默认 `Psola`**，
macOS/Windows 默认 `Vocoder`（PC-NSF-HiFiGAN 神经声码器，模型 `pc_nsf_hifigan.onnx` 56MB，
配 `fcpe.onnx` 神经 F0）。也就是用户在 Windows 上「导入→拖音符→听到的」是
**神经 F0 → mel → HiFiGAN 重合成**，波形由模型生成，源的毛刺不会被搬运过去。

PitchNet 有三条出声路径，别混：
1. **拖动音符试听** `ResampledLoopAudition::render` —— 纯线性重采样
   （`out[i] = src[i * pitchRatio]`，`pitchRatio = 2^(semi/12)`，-6dB）。零颗粒、零合成。
2. **最终渲染（默认）** —— HiFiGAN 声码器。
3. **经典 PSOLA** —— `IncrementalSynthesizer.cpp:1767` 的 `if (usePsola) … else …`，
   Linux 或推理失败才走。**第 3 条才是 `psola.rs` 的移植对象。**

所以「我们只有 PSOLA」对上「PitchNet 默认是神经声码器 / 拖动试听是纯重采样」，
听到的差异是**算法类别差异**，不是端口 bug。要真正对齐听感只能接神经声码器，
或在 PSOLA 前做谐波/噪声分离（噪声走时间映射重采样、不进颗粒重排）。

**后者已落地 = `hajimi_tx_run` mode 3**（见下面「降调沙沙的修法」一节）。
注意现象边界：**只有降调侧**——升调/原调（ratio ≥ 0.89）与 mode 1 **逐样本相同**。
用户原话「我们的高音处理可能比 PitchNet 表现好，只是低音越降越沙」，与此完全吻合，
所以修的时候**绝不能碰升调侧**。

#### 但是——**先读 PitchNet 自己的日志，不要靠读代码推测**

上面那三条路径是「代码上可能发生什么」。用户实际听到的是哪一条，**日志里有答案**，
读它的成本远低于猜错一次。而且本项目真的猜错过一次：靠代码推出「拖动试听 = 纯重采样」，
方向没错，但那台机器的 `liveAuditionEnabled` 是 `false`，那条路根本没响过。

| 文件 | 里面有 |
|---|---|
| `%APPDATA%/PitchNet/config.json` | `synthesisEngine`（`"Vocoder"`/`"PSOLA"`）、`liveAuditionEnabled`、`pitchDetector`、`device`、`lastFile` |
| `%APPDATA%/PitchNet/Logs/debug_<会话>.log` | **每次渲染一行** `synthesizeRegion: engine=Vocoder\|PSOLA … <耗时>` |
| `%APPDATA%/PitchNet/Logs/vocoder_<会话>.txt` | 模型加载路径与执行设备（`Execution device set to: CPU`） |

```bash
# 一句话统计「这台机器历史上用过哪个引擎」
cd "$APPDATA/PitchNet/Logs" && grep -h "synthesizeRegion: engine=" debug_*.log \
  | sed 's/.*engine=//' | awk '{print $1}' | sort | uniq -c
```

**2026-09-19 实测**：`config.json` = `"synthesisEngine": "Vocoder"` + `"liveAuditionEnabled": false`；
4 个会话合计 **152/152 次 `engine=Vocoder`，0 次 PSOLA、0 次回退**。
→ 用户**从未听过** PitchNet 的 PSOLA，他对比的对象 100% 是神经声码器。
**这种时候不要再去修 PSOLA 的「bug」** —— 先把这个事实告诉他，再谈路线选择。

顺带一个易读错的点：`vocoder_*.txt` 里只有一行 `Input names: mel`，看着像单输入；
实际 `Vocoder.cpp:411` 是 `inputTensorScratch.reserve(2)` + `melShapeScratch.resize(3)` /
`f0ShapeScratch.resize(2)` —— **两个输入：mel[T,128] + f0[T]**（日志只打印 `inputNames[0]`）。
而且 `IncrementalSynthesizer.cpp:1200` 的 mel 取自**导入时预算的源音频 mel**，变调时不改
→ 频谱包络固定 = **共振峰天然保持**。这就是它「干净又舒服、还不花栗鼠」的机制。

### ⚠ HNR 估计器坏了会伪装成「音频坏了」

本项目在这个探针上连踩两坑，两次都表现为「连干净的元音都量出负 HNR」——
是**估计器**坏了，不是音频坏了。所以 `--selftest` 是必须的第一步：合成已知白噪水平的
谐波信号，HNR 必须 >25dB 且随噪声**单调下降**。三条硬规矩：

1. **必须分数周期**。真周期如 137.14 样点，用 `round()` 的整数周期平均会在 K 个周期后
   彻底失相 → 谐波估计塌成 0 → 负 HNR。
2. **模板按归一化相位索引**（`i / P mod 1`），**不能**按 `i % L`（L = 模板长度）。
   后者每周期累积 (P−L) 样点漂移，175 周期后完全错位。
3. **逐帧（40ms）再取中位数**。周期同步平均假设整段周期与波形都不变；真语音有共振峰
   过渡与包络，段一长平均就抹开 → 残余被人为做大。

配套：探针第一参数也可以不是素材名，但要确认素材存在，否则脚本直接退出（找不到会 exit 2）。

### 已知未修：输出峰值超过满刻度（RMS 匹配 ≠ 峰值匹配）

局部增益匹配（`apply_local_gain_match`）比的是 **RMS**，对波峰因数变化是盲的：
10ms 帧的 RMS 窗（4 hop = 40ms）比瞬态长，于是爆音类素材的那几毫秒被按**平均值**补偿，
峰值冲出去。41 素材实测（`_probe-gain.mjs`）输出峰值 / 源峰值：

| 档位 | 峰增中位 | 峰增 max | 峰值 >1.0 的素材数 |
|---|---|---|---|
| +5 | 1.014 | 1.209 | 24/41 |
| -5 | 1.032 | 1.119 | 37/41 |
| +7 | 0.985 | 1.236 | 20/41 |
| ±12 | 1.00 / 1.15 | 1.387 | 21/41 / 40/41 |

源峰值本身全部 ≤1.0（0/41）。**PitchNet 的 `applyLocalGainMatch` 同样是纯 RMS 匹配、
同样没有输出上限** —— 差别在它的输出进 DAW 走浮点、由用户 trim；我们的输出直接进
Web Audio destination 与 `exporter.ts` 的 `Math.max(-1, Math.min(1, …))`，**会硬削顶**。

**当前默认链路其实能挡住**：`EQ3 → Compressor(-18dB/3:1, 5ms attack) → … → masterGain(-3dB)`，
0.95 峰值被压到约 -12dBFS。所以这一项**不是默认配置下的爆音来源**，但两个口子开着：
compressor 被旁路、或用户抬 masterGain。**若将来要修，正确位置是主总线加 ceiling
（brickwall limiter），不要在 `apply_local_gain_match` 里塞峰值限幅** ——
后者会让 RMS 匹配在「合成体既更尖又更轻」的帧上把电平压掉，可能反过来破坏那 1.000 的中位电平。

## 第三方变调引擎接入（分支 `feat/lib-engines`）

把「低音越降越沙」交给别的实现回答，**用户用耳朵投票**，而不是我们替他选。
默认零行为变化（偏好默认 `'wasm'`），只有用户在装配面板显式点选才走外部路径。
接入点只有一处：`sample-player.ts::playSample` 优先读全局偏好 ——
`exporter.ts` 与 `take-player.ts` 都经过它，所以**试听与导出同源**。

### roster：怎么核实「这个库号称 N 种算法」

**别凭宣传语接**。`@audio/shift` 的宣传语是「15 algorithms」，但 repo 里没有一个
`@audio/shift/algorithms.js` 之类的东西。核实方法是查 **meta 包的 `dependencies`**：

```bash
curl -s "https://registry.npmjs.org/@audio%2Fshift" \
 | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{
     const j=JSON.parse(s), v=j['dist-tags'].latest;
     console.log(Object.keys(j.versions[v].dependencies).join('\n'))})"
```

输出正好 15 个 `@audio/shift-*` 子包 → 「15」是真的。
（顺便：宣传语里的表有 **16 行**，多的那行是 `pitchShift` —— 一个按 `content`
自动选 psola/sms/transient 的**包装器**，不是算法，所以不接。）

**⚠️ 别直接 `import('@audio/shift')`**：meta 包的 `index.js` **静态 re-export 全部
15 个子包** —— 一旦 import 它，Vite 就把 15 个算法打进同一个 chunk，
按需加载全废。要接就装**子包**、`import('@audio/shift-xxx')`。想要它的自动选择能力，
自己写 3 行分发。

**逐个独立安装时注意传递依赖**：`@audio/shift-delay` 与 `@audio/spectral-pvoc`
可能只作为别的包的传递依赖躺在 `node_modules` 里 —— 直接 import 它们很脆，
要显式写进 `package.json`。

### 语义拆包（最容易接错）

- `@audio/shift-*` 的 `ratio` **只改音高**；`@audio/stretch-*` 的 `factor` **只改时长**。
  串联 = 先 shift 再 stretch，`τ=1` 时跳过第二步。
- **保不保共振峰是选型分水岭**：时域一族（`psola` / `wsola` / `ola` / `sample`）都是
  「伸缩 + sinc 重采样回原长」，**共振峰跟着 f0 走**（`shift-psola` 源码自述
  `formants move with f0 same as wsola`）；只有 `lpc`（LPC 源-滤波）与
  `formant`（倒谱包络）保共振峰。频域那一族的其余成员（声码器/SMS/HPSS）各有各的取舍。

### ⚠ 接任何第三方变调器，先跑这两个判据（都是本项目发明的，很省时间）

先验「时长契约」是**必要但不充分**的 —— 下面第 2 条说明为什么。

**1. 尾巴标记测试（决定性，唯一可信）**

造「音 − 静音 − 音」三段合成信号（各 0.3s），量
`输出尾部 25% 能量 / 头部 25% 能量`：

- 正经变调器 ≈ **1.0**（两段音都在）
- 播放速率型 ≈ **0.0**（第二段音根本没读到）

为什么必须有它：`@audio/shift-sample` 是播放速率式纯重采样，自述
`No time preservation: output duration = input_length / ratio, zero-padded`。
它**通过所有常规判据** —— 输出数组长度与输入完全相等、电平对（+0.3dB）、
f0 也确实降了。只有内容被按 ratio 压过，降调时**尾巴整段丢掉**。
长度 / 电平 / HNR 一个都发现不了。

**必须同时跑正弦与噪声两版**：`lpc` 那类源-滤波算法在**纯正弦**上会退化
（该库原话：AR 包络就是那个分音，滤波器锁住它），只用正弦会冤枉它 ——
实测 `lpc` 正弦 **0.124** / 噪声 **0.952**，`ola` 正弦 0.494 / 噪声 0.914。
**判据以噪声列为准。**

**2. 包络时间比 `a`（辅助，判读方式极易错，别单独用它定罪）**

把输出的 RMS 包络去和「源包络按 `a` 倍重采样」比，取最匹配的 `a`
（5ms 帧，`pred[i] = srcEnv(i·a)`）。`a≈1` = 内容时间轴没变。

- **陷阱一：不能只看 argmax。** RMS 包络平滑慢变，整体拉伸一点依然高度相关，
  峰值很**平** —— `psola`/`wsola`/`ola`/`delay`/`lpc` 的 argmax 落在 0.78~0.90，
  但 `a=1` 处与 argmax 处的匹配度只差 0.00~0.03。按 argmax 报会把它们
  **全部误判**成「内容被改过」——正是本项目最忌讳的那类假结论。
- **陷阱二：增益大 ≠ 真被改。** 要看判别量 `aCorr − atOne`。实测 SoundTouch 三个引擎
  在 −12 档增益涨到 **+0.28~0.46**（a≈0.6≈ratio），但尾巴标记证明它们
  **完全没丢内容**（1.005/1.007/1.084）—— 最可能是流水线**内部延迟**把包络整体推后，
  而没有 lag 参数的 scale 拟合会把延迟吸收成「轻微压缩」，大降调时吸收得更多。
- 只有 `sample` 的增益是压倒性的（−8 档 +0.544 / −12 档 +0.984）**且被第 1 条独立证实**。

> **通用教训**：一个「平滑的、没有参数解释延迟」的相似度指标，天然无法区分
> 「内容被拉伸」与「内容被延迟 / 包络被磨平」。**要么给它加 lag 维，要么别用它定罪。**
> 本项目已有两次同类教训（HNR 奖励净化、包络增益混淆延迟）。

### ⚠ 流式引擎接进同步内核：**先验「时长契约」，别先听波形**

SoundTouchJS（`@soundtouchjs/core`）是**流式**引擎（`putSamples` / `process` / `receiveSamples`），
而 `playSample` 是「整块进整块出」。必须写个离线驱动把它「泵」进泵出。
三个已经踩过的坑：

1. `SampleBuffer` 是**立体声交错**（每帧 L,R）→ 单声道素材要复制成 L=R；
2. 只设 `st.pitch = ratio` 就够了（内部派生 `_rate` / `_tempo` 并**自动交换串联顺序**），
   别自己拼两段式；
3. **必须尾部补静音**（`PAD_SEC=0.3`）再按输入帧数裁回 —— 输入喂完后 `process()` 不会吐残余，
   库里也**没有 `flush()`**。实测 0.720s 的源出 0.630s，**尾巴被静默截掉 12.5%**；
   而听感上只表现为「结尾短了一截」，很容易被当成「素材本来就这样」放过去。

> **通用教训**：接任何第三方 DSP 引擎，第一件事是量「输出帧数 == 输入帧数」。
> 波形好不好听是主观的、要听很多遍；时长对不对是**一秒钟就能验的客观判据**，
> 而且它坏了以后所有 A/B 听感对比都不可信（你比的是两段不同长度的音频）。
> **但长度合规不等于内容完整** —— 再加一条尾巴标记测试（见上）。

另：库内**只注册了 `'lanczos'`**，写 `strategy: 'linear'` 会抛
`Unknown interpolation strategy id "linear"` —— **d.ts 里 `@defaultValue 'linear'` 是错的**。
（又一次印证「注释比代码更该怀疑」。）

### 打包：第三方库必须走**字面量** `import()`

Vite 只对**字面量**做静态分析并切 chunk。换成变量写法（`import(path)`）会退化成
「运行时才知道要加载谁」，既打不出独立 chunk、也不进首屏预算。
实测 `soundtouch-engine` 独立 chunk = 33.9KB / **gzip 9.1KB**，不进首屏。

### ⚠ 切换引擎最坏的不是「切不过去」，而是「切过去了没生效却不说」

**症状**：用户报「引擎切换不稳健」/「有时生效有时不生效」，界面上完全看不出问题。

**根因是一类状态设计错误**：「用户选了谁」与「那个库真的能用了吗」是**两件独立的事**——
前者存在 localStorage 里能活过刷新，后者只是模块内存。而 `playSample` 只认
`getActiveShift()`，返回 null 时整个外部分支被**静默**跳过 → 面板高亮着第三方引擎、
耳朵里是 wasm。2026-09-20 探针实测复现：刷新后 `choice='st-long'` 但
`shiftReady=false`、`willUseExternal=false`（连加载都没发起）。

**修法四条**（都已落地，探针第 8 节 10 条钉住）：

1. **启动即自愈**：模块级 `void restoreEngine()`。放模块级而不是组件的 `useEffect`
   —— `sample-player.ts` 静态 import 了该模块，任何入口启动都会走到，
   不依赖「这一会话打开过装配面板」（否则「直接导出」会拿 wasm 渲出来）。
2. **允许重试**：点「已选中」的 chip 也要能重新加载（早退条件是 `next===choice && ready`，
   不能只比 choice），否则失败后用户没有任何办法救回来。
3. **切换要等依赖链就绪**：τ≠1 时时间伸缩是串联第二级，必须 `await`，
   否则切完的**第一声**还是旧引擎。`void` 掉一个 `await` 就是「时好时坏」。
4. **界面不许骗人**：暴露 `getEngineStatus()` / `getEffectiveEngine()`，
   UI 的高亮表示「选择」、说明文案描述「正在发生的事」，未就绪时明说此刻是 wasm。

**通用规矩**：任何「用户可选的内核」都要把**选择**与**就绪**分成两个状态，
并且把「实际生效的是哪个」渲染出来。只要存在「选择了但不可用仍静默降级」的路径，
用户迟早会把它描述成「不稳健」。

**另一条排查线（先排除掉，省时间）**：别急着怀疑引擎本身。写个电池脚本，
让每个引擎跑**全部素材**，查「抛异常 / 输出时长违约 / 疑似空转（输出与输入归一化
互相关 >0.99）/ 电平偏离」。实测 **19 个对象 × 41 素材全零**（电平偏离只有
`paulstretch` 3 个与 `ola` 4 个）—— 引擎是干净的，问题全在切换状态机上。

跑电池前先确认**解析路径**：`.workbuddy/tmp/libsurvey/` 下曾藏着一份
`node_modules`，`shift-transient` / `shift-delay` 会解析到**旧版本**，
实测结果和 App 实际打包的版本对不上。用 `createRequire` 逐个打印 `resolve()` 确认
全部落在项目根。（脚本：`.workbuddy/tmp/libsurvey/probe-all15.mjs`。）

## 会给出假结论的陷阱（都踩过）

### 0. 参考实现的「注释」往往比「代码」更该照抄

我们逐行移植 PitchNet。它的 `kMinEnvelope` 注释写的是「用 floor 留下**平滑的幅度凹陷**」，
而代码是 `if (weight > kMinEnvelope) output = padded / weight;`（`output` 初值 0）——
**满幅 ↔ 精确 0 的硬跳变**。逐行照抄代码，就把这个跳变一起抄了进来。

**判据**：拿几何算一下这个「下限」什么时候会被触到。Σw 在颗粒接缝处
= 2·Hann(A/2)，而 voiced 路径 A/grain_half = 1/ratio → 阈值是一个**具体的半音数**
（本例 ratio = 2/3 = -7.02 半音）。当参考注释描述的现象（平滑凹陷）与代码行为（硬置零）
矛盾、且代码行为恰好在某个参数值上发生**不连续**时，**优先信注释、按注释改**，
然后用 `_probe-clickcount.mjs` 扫参数轴验证。

修法通常就是把闸门写成除数下限：`padded / max(Σw, floor)`。w = floor 两侧都是
`padded/Σw`，天然连续；w → 0 时平滑收敛到 0 —— 正是注释里说的那个凹陷。

**移植 PitchNet 时的通用动作**：凡是看到 `if (x > C) { … } else { 0 }` 这种
「低于常量就归零」的写法，先问一句「x 在这个常量附近是连续变化的吗？」。
是 → 大概是闸门 bug；否 → 才是真正的「无效区」。

### 1. 别用纯正弦或「合成元音」验收 ±10 半音以上的电平

同一个内核、同一段名义内容，差四个数量级：

| 输入 | +12 半音后 RMS / 源 RMS |
|---|---|
| 单频正弦（`make_sine`） | **0.0001** |
| `make_vowel`（逐谐波 `sin(2π f i / sr + φ)`） | **1.0001** |
| 逐样本相位积分的谐波堆（严格周期） | **0.000** |

原因：`make_vowel` 逐谐波算 `sin(2π f i / sr + φ)`，高次谐波的相位参数（f·i ≈ 1e9）早已
越过 f32 精度，谐波实际是数值噪声 —— **严格周期被破坏，反而绕开了相干抵消区**。
所以拿它验收高变调比，量到的是合成信号的数值巧合，不是算法表现，会给出**虚假的安全感**。
要用真单频正弦（f·i 最大 1.9e7，f32 足够）或带脉冲激励的类声源。

### 2. 别信「一段」的结论

F0 只测中段，就会漏掉尾段漏变调；只测两端，就会漏掉中段塌陷。四段 + 全长 RMS 包络一起看。

### 3. 改前先确认「这不是既有问题」

项目里有脆弱的既有测试（例如 `effect-units/prototype-reverb.test.ts` 的噪声 IR 峰值断言）。
失败时先看 `git status` 与文件 mtime：**目录未被改动 ≠ 测试是好的**，但能确定不是你引入的。
反过来，如果 `tsc --noEmit` 报 `Settings` 缺字段，多半是有人给类型加了字段却没更新测试 fixture。

同一招也用于判定测试自身有 bug：`autotune.test.ts` 的 `centsOff` 曾写成
`1200 * (hzToMidi 差)`，而 `hzToMidi` 返回**半音** → 报出来的数字是真实音分的 12 倍
（43 音分其实只有 3.6）。看到「超限但只超一点」时，先怀疑单位。
